# 🐛 BUG: `Tools.merge()` byte-array corruption

## Meta
- **ID**: BUG-003
- **Type**: Bug
- **Status**: resolved (Phase 1, task 1.3)
- **Severity**: High
- **Created**: 2026-09-19
- **Affected**: `tools/Tools.java:294-308` (`merge()`); no production call sites currently exist

## Summary
The inner loop in `merge()` never increments its position counter, so every byte from every input array is written to index 0 of the result buffer, silently corrupting the merged output.

## Actual Behavior
Confirmed by code read: the counter variable used as the write index is not incremented inside the copy loop (lines ~294-308). Every array element overwrites index 0; only the very last byte written survives at position 0, the rest of the returned buffer is left as its default/garbage state.

## Expected Behavior
`merge()` should concatenate all input byte arrays correctly, preserving every byte at its correct sequential offset.

## Steps to Reproduce
1. Call `Tools.merge()` with multiple byte arrays containing distinct patterns.
2. Inspect the merged result — before the fix, content beyond index 0 was not what was passed in.

## Error Messages
No crash — silent data corruption for any future caller of the utility.

## Environment
- Version: 1.1.2 (branch `master`)
- Phase: 1 — Security & Stability Hardening

## Acceptance Criteria
- [x] `merge()` correctly concatenates arrays
- [x] Unit test added covering multi-array merge with distinct byte patterns per array
- [x] Confirmed no caller depended on the buggy index-0-only behavior

## Fix

Replaced the inner byte loop with `System.arraycopy` at a monotonically increasing offset and added an explicit aggregate-length overflow guard. Three JVM tests cover empty input, a single array with independent output storage, and ordered concatenation across empty/distinct segments.

A repository-wide call-site scan corrected the original audit attribution: `Recognizer.headers.merge(cachedSaved)` invokes `io.grpc.Metadata.merge`, not `Tools.merge`. There are currently no production callers of this utility, so no code depended on its corrupt output.
