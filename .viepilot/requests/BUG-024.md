## Summary

Both foreground voice services dereference the `Intent` argument in `onStartCommand(...)` without checking for `null`. Android may restart a sticky service and call `onStartCommand(null, ...)`, so the current code can crash during process/service recovery.

## Evidence

- `VoiceTranslationService.java:136-140` reads `intent.getParcelableExtra("notification")`.
- `WalkieTalkieService.java:77-79` reads both language extras from `intent`.
- Android's `Service` contract explicitly permits a null intent when a service is restarted after its process is killed.
- The risk was mentioned as an adjacent finding in resolved `BUG-010`, but it was never implemented or covered by tests.

## Details

- **Tier**: 3
- **Audit date**: 2026-09-26
- **Affected files**: `VoiceTranslationService.java`, `WalkieTalkieService.java`

## Desired behavior

Service restart with a null intent must be deterministic and non-crashing. Each service must either restore sufficient persisted/default state and continue, or stop itself cleanly when required launch data is unavailable.

## Acceptance criteria

- [ ] Both `onStartCommand(null, flags, startId)` paths are handled without a crash.
- [ ] The restart policy/return value is explicit and consistent with the state that can actually be restored.
- [ ] Notification and language state are not silently replaced with invalid values.
- [ ] JVM or instrumentation regression coverage exercises both null-intent paths.
- [ ] Existing normal-start, cancel, close, and foreground-service tests remain green.

## Scope guard

Do not use this fix to redesign engine selection, Bluetooth transport, onboarding, or release signing.

## Resolution

Resolved by `8a8882b`. Both services validate null restart intents before reading extras; the base voice service stops the restarted instance and returns `START_NOT_STICKY`. `ServiceRestartContractTest` guards both source paths. Full JVM/instrumentation/lint gates passed.
