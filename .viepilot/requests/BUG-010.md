# BUG: WalkieTalkieService teardown can unbind unregistered connections

## Meta

- **ID**: BUG-010
- **Type**: Bug
- **Status**: fixed locally, pending PM review (Phase 2, task 2.4)
- **Severity**: Medium
- **Created**: 2026-09-19
- **Affected**: `voice_translation/_walkie_talkie_mode/_walkie_talkie/WalkieTalkieService.java`

## Summary

Before the fix, `onDestroy()` unconditionally called
`unbindService(firstLanguageConnection)` and `unbindService(secondLanguageConnection)`, although
binding is conditional in `onStartCommand`. This could unbind a connection for which this service
instance had never made a bind attempt.

## Actual Behavior Before Fix

If the service was destroyed before the conditional bind branch ran, both connections were
unbound unconditionally and Android could throw `IllegalArgumentException: Service not
registered`. A low-memory process kill followed by `onDestroy` is not treated as a deterministic
Android lifecycle sequence; the controlled reproduction is destroy-before-bind.

## Expected Behavior

For each recognizer `ServiceConnection`, track every `bindService` registration attempt and make
one matching `unbindService` call for each attempt. This must not depend on `bindService`
returning `true` or on `onServiceConnected`: Android's `Context.bindService` contract requires a
later `unbindService` even when the bind call returns `false`.

## Controlled Reproduction Before Fix

1. Create the service lifecycle state, then invoke teardown before `onStartCommand` reaches either
   recognizer bind attempt.
2. Before the fix, `onDestroy` invokes both direct `unbindService` calls and can throw `Service
   not registered`.
3. The focused `WalkieTalkieServiceBindingSourceTest` fails against that old direct
   paired-unbind implementation. `BindingAttemptTrackerTest` controls no-bind, one-connection,
   false-return, both-connection, repeated-attempt, and cleanup-error states without requiring a
   real recognizer or credential.

## Error Messages

`java.lang.IllegalArgumentException: Service not registered: ...`

## Environment

- Version: 1.1.2 (branch `master`)
- Phase: 2 - Correctness & Robustness

## Acceptance Criteria

- [x] Destroy-before-bind performs zero unbinds.
- [x] One recognizer attempt, a false-return attempt, and each normal recognizer attempt receive
  exactly one matching unbind.
- [x] Repeated bind attempts are released once each; cleanup failures are logged and do not stop
  later local cleanup or `super.onDestroy()`.
- [x] No binding state is inferred from `IllegalArgumentException`, `bindService`'s return value,
  or `onServiceConnected`.

## Adjacent Finding: `onStartCommand(null)`

`WalkieTalkieService.onStartCommand` dereferences `intent` at its first
`getSerializableExtra` call, and the parent `VoiceTranslationService.onStartCommand` also
dereferences it for `notification`. This is an independent null-intent risk, not an implicit part
of BUG-010. Proposed separate task: define the service restart policy and add a null guard in both
overrides (including an explicit result for a restart without languages/notification) before
changing behavior.

## Fix and Verification

`BindingAttemptTracker` counts attempts separately for the two recognizer connections.
`WalkieTalkieService` records an attempt immediately before each `bindService` call, regardless of
its boolean return value, and consumes one count for every teardown unbind. Communication
shutdown, both connection releases, and the parent teardown are allowed to continue when a local
cleanup action throws; exceptions are logged rather than used as state.

Focused JVM regression passed 7/7 after the fix; the same focused source test failed 1/1 before
the fix. Full `testDebugUnitTest` passed 30/30, `assembleDebug` passed, and the available API 36
emulator passed its existing 5/5 instrumentation tests. The project currently has no
instrumentation harness that constructs this TTS/recognizer service through its complete Android
lifecycle; the controlled lifecycle-state coverage is therefore JVM-level. `lintDebug` completed
with 5 errors and 121 warnings, all retained as the existing project baseline rather than being
claimed clean by this task.
