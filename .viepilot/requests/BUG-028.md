# BUG: Persisted mode restore can re-enter a Conversation crash loop

## Summary

`VoiceTranslationActivity.onStart()` executes the fragment number stored in preferences without checking whether a Conversation service or Bluetooth peer is still valid. Conversation is persisted before its service has safely started, and a terminal peer disconnect stops the service without resetting the persisted fragment. The physical `BUG-026` incident demonstrated the impact: one startup exception was replayed on every launch and made the app appear permanently unusable.

## Details

- **Tier**: 3
- **Audit date**: 2026-09-28

- Evidence: `VoiceTranslationActivity.java:142-147` restores the saved value directly; `:190-203` persists Conversation immediately; `ConversationService.java:143-146` stops after the last peer disconnect but does not clear or downgrade the saved mode.

## Acceptance Criteria

- [ ] A cold process start treats a saved mode as a UI hint, not authorization to execute a stale service/session.
- [ ] Conversation restores only when a valid active session can be proven; otherwise startup falls back recoverably to Pairing.
- [ ] Last-peer disconnect and terminal service failure cannot leave an executable stale Conversation preference.
- [ ] A focused API 36 test injects a startup failure and proves the next launch reaches a safe screen instead of replaying the failure.
- [ ] Normal background/foreground continuity for a genuinely active service remains intact.
- [ ] Re-run vp-audit: this finding no longer appears.

## Resolution

2026-09-28: cold-start restoration now accepts Conversation only when a connected peer proves a live session; stale/unknown values fall back to Pairing. Preference writes capture the value without a raw thread, and final-peer/service termination persists Pairing. JVM policy tests plus an API 36 stale-Conversation launch test passed. Same-two-phone background/relaunch validation remains Task 9.7.
