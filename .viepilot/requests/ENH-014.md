# 🔧 ENHANCEMENT: Constrain Java deserialization in `Tools.objToByte`/`byteToObj`

## Meta
- **ID**: ENH-014
- **Type**: Enhancement
- **Status**: new
- **Created**: 2026-09-19
- **Breaking**: No

## Summary
`tools/Tools.java:310-331` (`objToByte`/`byteToObj`) uses `ObjectOutputStream`/`ObjectInputStream` (never closed — a separate minor leak) and `byteToObj` deserializes arbitrary bytes via `ObjectInputStream.readObject()` with no allow-list. Currently only used internally, so this is low risk today, but Java deserialization of untrusted input is a classic gadget-chain vector if the byte source ever becomes external/untrusted (e.g. received over Bluetooth or network in a future feature).

## Current Feature
Internal object serialization helper.

## Current Behavior
No allow-list on deserialization; streams not closed.

## Desired Improvement
Close streams via try-with-resources; add a documented constraint (or an allow-listing `ObjectInputStream` subclass) so this helper is never used to deserialize data received from outside the app process without review.

## Value Proposition
Cheap to fix now (stream leak) and cheap insurance against a much worse bug later if this helper is ever repurposed for network/Bluetooth payloads.

## Acceptance Criteria
- [ ] Streams closed via try-with-resources
- [ ] Comment or guard added noting this must not be used on untrusted/external byte sources without an allow-list
