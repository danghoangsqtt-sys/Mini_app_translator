# 🐛 RISK: Vendored GraphView has an unreachable second-scale auto-bounds branch

## Meta
- **ID**: BUG-012
- **Type**: Future-risk / dead-code capability
- **Status**: PM accepted locally as Low/future capability; no production fix; remote persistence and quality gate pending (Phase 2, task 2.6)
- **Severity**: Low
- **Created**: 2026-09-19
- **Affected**: `tools/gui/graph/GridLabelRenderer.java:608`

## Summary
The vendored copy of the GraphView charting library (Jonas Gehring, Apache-2.0, copy-pasted into the app package rather than pulled as a dependency) retains a branch that does `throw new IllegalStateException("Not yet implemented")` for non-manual Y-axis bounds on the second scale. Current application code cannot create or configure that state, so this is a future-capability risk rather than a current app bug.

## Actual Behavior
Future code that adds a series to the second scale and exposes automatic Y bounds could reach the throw. The current graph feature never calls `GraphView.getSecondScale()` and has no runtime path to change the second scale from manual bounds.

## Expected Behavior
Do not change the vendored throw while it is unreachable. Any future feature that uses the second scale must either implement and test auto-bounds (including empty and degenerate datasets), or preserve manual-only bounds deliberately.

## Steps to Reproduce
There is no current UI reproduction. The only application GraphView is `DateGraph` in
`component_credit_graph.xml`, created by `CustomDayGraphsPagerAdapter`; it never calls
`getSecondScale()`. Reproduction would require a future code/API change or unsupported reflective
mutation of the vendored private flag.

## Reachability Evidence and Follow-up

`SecondScaleReachabilityProofTest` scans production Java outside the vendored graph package and
layouts. It verifies no application `getSecondScale()`/`SecondScale` use, the one known `DateGraph`
layout, and the manual-only vendored API. Manual inspection found internal library calls to
`getSecondScale()` in renderers/series; these are not callers from application code. A production
source reflection search (`Class.forName`, reflective method lookup/invocation, `setAccessible`)
found no path that could mutate the private flag. The proof cannot rule out a modified APK, a new
feature, or native/debugger reflection, so future second-scale work must reopen this request.

available API 36 emulator passed 7/7 instrumentation tests. `lintDebug` remains the separate
