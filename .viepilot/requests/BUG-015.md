# 🐛 BUG: Foreground voice services lack required service types and permissions

## Meta
- **ID**: BUG-015
- **Type**: Bug
- **Status**: reopened by vp-audit 2026-09-29; promotion-order residual remains before physical release QA
- **Severity**: High
- **Created**: 2026-09-20
- **Affected**: `app/src/main/AndroidManifest.xml:18,68-72`, `app/src/main/java/nie/translator/rtranslatordevedition/voice_translation/VoiceTranslationService.java:249`

## Summary
The original audit found foreground services without types. The manifest now declares `microphone|connectedDevice` service types and the matching normal permissions; runtime ordering and Android 14+ behavior still require device validation.

## Actual Behavior
Only `android.permission.FOREGROUND_SERVICE` is declared, and `startForeground(11, notification)` is called without a declared service type.

## Expected Behavior
Declare the precise foreground service types and their matching permissions, then start foreground work only after runtime prerequisites such as `RECORD_AUDIO` and Bluetooth permissions are granted.

## Acceptance Criteria
- [x] Each foreground service has the minimum correct `android:foregroundServiceType`
- [x] `FOREGROUND_SERVICE_MICROPHONE` and/or `FOREGROUND_SERVICE_CONNECTED_DEVICE` are declared where required
- [x] Foreground promotion uses a compatible API that supplies the active type on supported Android versions
- [ ] Starting Conversation and WalkieTalkie modes on Android 14+ does not throw `MissingForegroundServiceTypeException` or `SecurityException`
- [ ] Background-start restrictions and permission ordering are covered by tests or a documented device test matrix

## Fix
Implemented in Phase 3 Cluster A. Keep the request in progress until the required Android 14+ foreground-service and Bluetooth device matrix passes.

## Discussion

Re-detected by vp-audit 2026-09-28: manifest types/permissions are present, but runtime promotion still uses `startService()` in `VoiceTranslationActivity.java:535-566` and defers `startForeground()` until `VoiceTranslationService.onUnbind()` (`:260-285`). Android's current documented lifecycle is `startForegroundService()` followed by prompt foreground promotion, ordinarily in `onStartCommand()`. Keep this request open until background/foreground transitions on API 31/34/36 prove the current ordering or the lifecycle is corrected.

## Resolution update

Task 9.10 implementation `cc08c4f` launches both modes through `ContextCompat.startForegroundService`, promotes in `onStartCommand`, keeps the service foreground across binding, removes the notification on teardown, and narrows Walkie to microphone-only while Conversation retains microphone plus connected-device. API 36 automated gates pass; physical API 31/34/36 foreground/background behavior remains Task 9.7 evidence.

## 2026-09-29 deep-audit residual

The caller-side permission preflight in `a9d04d7` closes the reproduced missing-microphone path, but foreground promotion is still not the first meaningful service operation:

- `VoiceTranslationService.onCreate()` constructs TTS and the speech-output adapter before `onStartCommand()` can promote the service.
- `ConversationService.onCreate()` additionally creates the on-device engines, handler/coordinator, wake-lock timer, Bluetooth headset helper/callback, and starts the helper before promotion.
- `WalkieTalkieService.onCreate()` creates the engines/controller, and `onStartCommand()` applies languages before delegating to the promoting base implementation.
- `promoteToForeground()` catches any runtime failure, emits a generic callback that may have no client yet, calls `stopSelf()`, and leaves the original `startForegroundService()` contract unfulfilled. This is the same platform failure class previously observed in `BUG-032`.
- The Conversation wake-lock reactivation callback has no `closed` guard, while teardown posts timer cancellation asynchronously; a timer race can reacquire after service destruction.

Android invokes `Service.onCreate()` before `onStartCommand()` and requires a service launched with `startForegroundService()` to call `startForeground()` within five seconds. Therefore slow TTS/Bluetooth/engine initialization on a physical OEM device can still produce an ANR or `ForegroundServiceDidNotStartInTimeException` even when permissions were valid at the caller.

### Additional acceptance criteria

- [ ] Foreground promotion occurs before TTS, ML Kit, recognizer, wake-lock, Bluetooth-helper, or controller initialization.
- [ ] Initialization begins only after promotion succeeds and has one rollback path that clears the persisted mode and shows an actionable error.
- [ ] Promotion failures are observable before a client is bound and cannot leave a `startForegroundService()` deadline outstanding.
- [ ] Teardown prevents wake-lock timer callbacks from reacquiring resources after `onDestroy()`.
- [ ] Runtime tests inject delayed/failing initialization and prove both services remain crash/ANR-free beyond the foreground deadline.
