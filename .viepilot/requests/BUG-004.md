# 🐛 BUG: `Recorder` stop/release race with the recording thread

## Meta
- **ID**: BUG-004
- **Type**: Bug
- **Status**: resolved (Phase 1, task 1.4)
- **Severity**: High
- **Created**: 2026-09-19
- **Affected**: `voice_translation/cloud_apis/voice/Recorder.java:130-143` (`stop()`), background thread at line ~208 (`ProcessVoice`)

## Summary
`stop()` calls `mThread.interrupt()` then immediately `mAudioRecord.stop()/release()`, but the background thread is typically blocked inside `AudioRecord.read()`, which is not interruptible — so it may still be executing `read()` on an object concurrently released by the caller thread.

## Actual Behavior
Rapid stop/start of the microphone (e.g. TTS interrupting listening) can race the release of `mAudioRecord` against an in-flight `read()` call on the same object.

## Expected Behavior
`stop()` should ensure the reading thread has actually exited its read loop (e.g. via a flag checked after each `read()` call, joined with a timeout) before releasing the `AudioRecord`.

## Steps to Reproduce
1. Start voice recording (Conversation or WalkieTalkie mode).
2. Trigger a rapid stop (e.g. interrupt via TTS output) while audio is actively being captured.
3. Repeat under load — intermittent crash or corrupted recorder state.

## Error Messages
Likely `IllegalStateException` from `AudioRecord` or a native crash, intermittent/timing-dependent.

## Environment
- Version: 1.1.2 (branch `master`)
- Phase: 1 — Security & Stability Hardening

## Acceptance Criteria
- [x] `stop()` no longer releases `AudioRecord` while the reader thread may still be in `read()`
- [x] Regression/stress test exercises 100 blocked-read stop cycles
- [x] Normal stop/start callbacks and capture flow are preserved

## Fix

Recorder lifecycle methods are serialized. Stop sets a volatile shutdown flag, invokes `AudioRecord.stop()` to unblock an active read, interrupts and joins the reader with a bounded wait, and clears the session only after the reader exits. The capture thread holds session-local references and is the sole owner of `AudioRecord.release()` through its `finally` block. If shutdown times out, the session remains retained and a new recorder cannot overlap it.

A pure-Java coordinator regression ran 100 simulated blocked-read shutdowns and verified stop-before-release ordering plus reader termination. Unit tests, lint, and debug assembly passed; physical microphone stress remains part of the Phase 1 device gate.
