# 🐛 BUG: gRPC streaming `onError` silently swallowed in `Recognizer`

## Meta
- **ID**: BUG-005
- **Type**: Bug
- **Status**: resolved (Phase 1, task 1.5)
- **Severity**: High
- **Created**: 2026-09-19
- **Affected**: `voice_translation/cloud_apis/voice/Recognizer.java:134-137`

## Summary
`mResponseObserver.onError(Throwable t)` has its body commented out (`//callback.onError();`). Any network/auth/gRPC failure during streaming speech recognition is dropped silently.

## Actual Behavior
When the gRPC stream errors (network loss, auth failure, quota exceeded, etc.), nothing is propagated to the UI/service layer. The `recognizing` state goes out of sync and the conversation can silently stop transcribing with no error shown to the user.

## Expected Behavior
`onError` should invoke the actual error callback so callers can surface a message, retry, or reset recognizer state appropriately.

## Steps to Reproduce
1. Start a conversation/walkie-talkie session.
2. Force a network drop or invalid/expired credential mid-stream.
3. Observe that recognition simply stops with no error feedback to the user.

## Error Messages
None surfaced — that's the bug.

## Environment
- Version: 1.1.2 (branch `master`)
- Phase: 1 — Security & Stability Hardening

## Acceptance Criteria
- [x] `onError` implementation resets stream state and notifies the caller
- [x] Service/UI behavior is defined through existing error callbacks; the listen session ends and the user sees the mapped error
- [x] Tests simulating stream errors confirm exactly-once callbacks and stale-event isolation

## Fix

Each recognition stream now owns a generation-specific response observer. `onError` passes through a terminal gate, maps gRPC connectivity/authentication/other failures to the app's existing error reasons, clears recognizing/request/queued-audio state, and invokes `RecognizerListener.onError`. The established service callback route ends the listen session and surfaces the error to the UI. Completed, destroyed, duplicate, and stale stream events are ignored safely; no automatic retry is attempted for invalid credentials or unknown failures.

Three JVM tests cover error mapping, exactly-once delivery, teardown suppression, and a late error from a replaced stream. Unit tests, lint, and debug assembly passed.
