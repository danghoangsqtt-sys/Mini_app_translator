# 🐛 BUG: AES/CTR encryption helpers used without a MAC (malleable ciphertext)

## Meta
- **ID**: BUG-008
- **Type**: Bug
- **Status**: new
- **Severity**: Medium
- **Created**: 2026-09-19
- **Affected**: `tools/Tools.java:258,284` (`encript`/`decript`), error paths at 262-264, 288-290

## Summary
`Tools.encript`/`decript` use AES/CTR with no MAC/authentication (no HMAC, no GCM) — ciphertext is malleable (bit-flippable without detection). Additionally, crypto failures (`InvalidKeyException` etc.) are only `printStackTrace()`'d and return `null`, so callers may silently proceed with a `null` key/ciphertext.

## Actual Behavior
Encrypted data protected only by these helpers can be tampered with undetected; crypto exceptions are swallowed rather than surfaced.

## Expected Behavior
Use an authenticated mode (AES/GCM) or add an HMAC over the CTR ciphertext; propagate crypto failures to callers instead of returning `null` silently.

## Steps to Reproduce
1. Locate a call site using `Tools.encript`/`decript` on sensitive data.
2. Flip a bit in the stored ciphertext — decryption "succeeds" with corrupted plaintext instead of failing.

## Error Messages
None surfaced on tamper — that's the issue. Genuine key errors currently only appear in logcat via `printStackTrace()`.

## Environment
- Version: 1.1.2 (branch `master`)
- Phase: 2 — Correctness & Robustness

## Acceptance Criteria
- [ ] Switch to AES/GCM (or add HMAC-then-encrypt/encrypt-then-MAC) for any data this helper protects
- [ ] Crypto exceptions propagate to the caller (checked exception or explicit failure result) instead of returning `null`
- [ ] Confirm actual call sites/sensitivity of data before prioritizing (may overlap with BUG-001 remediation if key storage moves to `EncryptedFile`, which would replace this helper's use)
