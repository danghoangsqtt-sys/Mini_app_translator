# 🐛 BUG: AES/CTR encryption helpers used without a MAC (malleable ciphertext)

## Meta
- **ID**: BUG-008
- **Type**: Bug
- **Status**: resolved (Phase 2, task 2.2; final gate passed and remote persistence verified)
- **Severity**: Medium
- **Created**: 2026-09-19
- **Affected**: legacy `tools/Tools.java` AES/CTR helper API (removed)

## Summary
The former `Tools.encript`/`decript` API used AES/CTR with no MAC/authentication (no HMAC, no GCM), making ciphertext malleable. It also returned `null` after logging crypto failures. Reachability review found no consumer in this fork, so the API has been removed rather than migrated.

## Actual Behavior Before Fix
Before removal, data protected by these helpers could be tampered with undetected, and crypto exceptions were swallowed rather than surfaced. No current production path can invoke this removed API.

## Expected Behavior After Fix
Production code must not expose or reintroduce the unauthenticated AES/CTR helper. Any future persisted crypto format must use authenticated encryption and return an explicit failure to its caller.

## Steps to Reproduce Before Fix
These steps describe the removed API and are retained only as historical evidence. They do
not apply to the current source tree: the live source and all 141 `master` ancestors show no
call site for this helper. The risk could be demonstrated on a pre-removal revision by calling
the helper directly in an isolated test.

1. On a revision that still contains the helper, call `Tools.encript` for known plaintext.
2. Flip a bit in the returned ciphertext and pass it to `Tools.decript`.
3. Observe that decryption can return corrupted plaintext rather than reporting tampering.

## Error Messages Before Fix
This section records the removed API's behavior.
None surfaced on tamper — that was the issue. Genuine key errors were only printed to logcat via `printStackTrace()`.

## Acceptance Criteria
- [x] Confirm actual call sites/sensitivity before changing behavior: live source and all 141 `master` ancestors contain no caller or persisted consumer.
- [x] Remove the unreachable unauthenticated helper API, so no sensitive data can use it and no `null` crypto failure path remains.
- [x] Keep credential persistence on its existing Keystore-backed AES-GCM implementation; no migration is needed for a format this app never wrote.

## Fix
Removed `encript`, `decript`, `decriptToString`, and `CipherData` from `Tools.java`.
The historical reachability scan found no serialized data contract or caller to preserve, so
there is no read-old/write-new migration. A source regression test prevents restoring the
unauthenticated AES/CTR transform. `CredentialStore` remains unchanged and continues to
authenticate credential ciphertext with AES-GCM.
