# 🐛 BUG: Stale delayed `Handler` runnable can fire after `ConversationService` teardown

## Meta
- **ID**: BUG-011
- **Type**: Bug
- **Status**: resolved (Phase 2, task 2.5; final gate passed and remote persistence verified)
- **Severity**: Medium
- **Created**: 2026-09-19
- **Affected**: `voice_translation/_conversation_mode/_conversation/ConversationService.java:57` (`static Handler mHandler`), `:348-354` (post), `:308-325` (`onDestroy`)

## Summary
`onScoAudioDisconnected()` posts a 1-second-delayed `stop()/start()` on `BluetoothHelper` via a `static Handler`. `onDestroy()` never calls `mHandler.removeCallbacksAndMessages(null)`, so a service destroyed within that 1-second window still runs the callback against a torn-down helper/service.

## Actual Behavior
Delayed callback can execute after the service and its `BluetoothHelper` have already been torn down, risking a crash or use of stale references. The `static` nature of `mHandler` is also an Android-lint-flagged leak pattern.

## Expected Behavior
Each `ConversationService` instance owns its delayed SCO reconnect runnable. `onDestroy()` marks
that instance destroyed and removes only its pending runnable before `BluetoothHelper` teardown.
Both queued and already-dispatched-but-late callbacks must check lifecycle/generation before
calling `stop()` or `start()`. A live service still reconnects normally; a replacement service
must not be affected by the old instance's callback.

## Steps to Reproduce
1. Trigger a SCO audio disconnect event during an active conversation (posts the delayed runnable).
2. Destroy the service (e.g. user ends conversation) within 1 second of that event.
3. Observe the delayed callback executing against a torn-down `BluetoothHelper`.

## Error Messages
Likely `NullPointerException` or similar, timing-dependent.

## Environment
- Version: 1.1.2 (branch `master`)
- Phase: 2 — Correctness & Robustness

## Acceptance Criteria
- [x] SCO reconnect work is owned by one `ConversationService` instance and cancels only its
  exact pending runnable.
- [x] A pending or dispatched-but-late callback cannot call helper `stop()`/`start()` after that
  instance is destroyed, including when a replacement instance is live.
- [x] Repeated reconnect requests replace only the preceding runnable for that instance; a live
  instance still reconnects.
- [x] The lifecycle-destroyed state is set before `BluetoothHelper.stop()` can emit callbacks.

## Adjacent Finding: wake-lock timer/reactivation

`startWakeLockReactivationTimer()` posts creation of a third-party `Timer`, whose callback calls
`acquireWakeLock()`. `onDestroy()` posts timer cancellation through the same main handler. This
task did not add a change because the timer has no controlled seam and no post-destroy callback
was reproduced. Treat this as a separate lifecycle test/fix request rather than assuming the SCO
guard protects it.

## Fix and Verification

`ScoReconnectCoordinator` now owns the delayed runnable, dispatcher, generation, and destroyed
state for one service instance. `ConversationService` uses its instance `mainHandler` to dispatch
that coordinator and calls `destroy()` before helper teardown; no shared handler queue is cleared.
The controlled JVM boundary test covers pending, dispatched-late, old/new instance, repeated, and
live reconnect cases without a Bluetooth device or credential. Verification passed: focused JVM
6/6, full `testDebugUnitTest` 36/36, `assembleDebug`, and API 36 instrumentation 7/7. `lintDebug`
still reports the existing 5 errors and 121 warnings (0 fatal), outside this task's diff.
