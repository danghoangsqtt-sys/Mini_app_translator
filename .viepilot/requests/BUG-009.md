# 🐛 BUG: Data race on `Global.apiToken`

## Meta
- **ID**: BUG-009
- **Type**: Bug
- **Status**: implemented locally; remote persistence pending (Phase 2, task 2.3)
- **Severity**: Medium
- **Created**: 2026-09-19
- **Affected**: `Global.java:438` (read), `Global.java:500` (write)

## Summary
Reads of `apiToken` happen inside `synchronized(lock)` (line 438), but the write `apiToken = credentials.refreshAccessToken();` (line 500) happens on a background thread outside any lock on `lock`, and the field is not `volatile` — a classic unsafe-publication bug.

## Actual Behavior
A thread calling `getApiToken(true, ...)` concurrently with a background token refresh can observe a stale or partially-visible `apiToken` reference.

## Expected Behavior
The write should either happen inside the same `synchronized(lock)` block used by readers, or the field should be `volatile` (or both, if ordering beyond visibility matters).

## Steps to Reproduce
Hard to reproduce deterministically — requires a token refresh racing a concurrent read under real threading; flag for code review + targeted concurrency test (e.g. via a controlled test harness forcing interleaving) rather than a manual repro.

## Error Messages
None reliably — manifests as an intermittently stale/invalid token used for an API call.

## Environment
- Version: 1.1.2 (branch `master`)
- Phase: 2 — Correctness & Robustness

## Acceptance Criteria
- [x] Token read, write, reset, pending-listener draining, generation, and refresh scheduling use one coordinator lock.
- [x] The token scheduler removes only its stored refresh runnable; it never calls `removeCallbacksAndMessages(null)` on a shared handler.

## Fix
`Global` now delegates token ownership to `ApiTokenCoordinator`. Credential loading and Google
token refresh remain on a worker thread, while app callbacks are posted to the main handler.
The coordinator invalidates older work with a generation counter and owns exactly one delayed
refresh runnable. This removes the mixed `this`/`lock` synchronization and the shared-handler
queue clearing that could cancel unrelated work.
