# 🐛 BUG: Two independent Room database instances on one SQLite file

## Meta
- **ID**: BUG-007
- **Type**: Bug
- **Status**: PM accepted locally; remote persistence and quality gate pending (Phase 2, task 2.1)
- **Severity**: Medium
- **Created**: 2026-09-19
- **Affected**: `api_management/ConsumptionsDataManager.java:34`, `voice_translation/.../RecentPeersDataManager.java:36`

## Summary
Both classes independently call `Room.databaseBuilder(context, AppDatabase.class, "consumption_credit_dp").build()`, creating two separate, non-singleton `AppDatabase` instances pointed at the same underlying SQLite file — against Room's explicit guidance.

## Actual Behavior
Concurrent writes from both managers can corrupt the DB or throw `SQLiteDatabaseLockedException`.

## Expected Behavior
A single shared `AppDatabase` singleton (e.g. held on `Global`/Application) should be injected into both managers.

## Steps to Reproduce
1. Trigger consumption-tracking writes (`ConsumptionsDataManager`) and recent-peer writes (`RecentPeersDataManager`) concurrently (e.g. during an active conversation while usage stats update).
2. Under load, observe lock contention or corruption.

## Error Messages
`SQLiteDatabaseLockedException` (intermittent, timing-dependent).

## Environment
- Version: 1.1.2 (branch `master`)
- Phase: 2 — Correctness & Robustness

## Acceptance Criteria
- [x] Single shared `AppDatabase` instance used by both managers
- [x] No behavior regression in either manager's existing queries
- [x] Record that no schema/data migration is needed for this ownership-only fix; migration design is deferred until the first schema version change (currently `version = 1`).

## Fix
`AppDatabase.getInstance(Context)` is now the sole production Room builder, using an
application context and double-checked locking. `ConsumptionsDataManager` and
`RecentPeersDataManager` both obtain that singleton while retaining their public
constructors and existing query/thread behavior. JVM and API 36 emulator regression
tests verify builder centralization and that `Hour` plus `RecentPeerEntity` rows survive
a close/reopen. Schema version remains 1; migration design belongs with the first
schema change rather than this ownership-only fix.
