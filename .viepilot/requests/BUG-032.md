# BUG: Missing microphone permission causes a foreground-service crash loop

## Meta
- **ID**: BUG-032
- **Type**: Bug
- **Status**: reopened residual by vp-audit 2026-09-29; base fix passes API 36, permission-result recreation remains unsafe
- **Priority**: Critical
- **Created**: 2026-09-29
- **Reporter**: Physical two-phone QA
- **Assignee**: AI

## Summary

After a fresh install, entering WalkieTalkie or transitioning into Conversation can terminate the process when microphone permission has not yet been granted. WalkieTalkie is persisted, so every relaunch re-enters the same failure and appears unusable until app data is cleared or the app is reinstalled.

## Deterministic reproduction

API 36 emulator reproduction from the 2026-09-28 debug APK:

1. Complete onboarding and enter WalkieTalkie once.
2. Force-stop the app and revoke `android.permission.RECORD_AUDIO`.
3. Relaunch; persisted WalkieTalkie starts its voice service.
4. Wait beyond Android's foreground-service promotion deadline.

Observed fatal:

`RemoteServiceException$ForegroundServiceDidNotStartInTimeException: Context.startForegroundService() did not then call Service.startForeground()`

The originating call is `VoiceTranslationActivity.startWalkieTalkieService()`; Conversation uses the same launch pattern.

## Root cause

The Activity calls `ContextCompat.startForegroundService()` before verifying the permissions required by the service's declared foreground type. When `RECORD_AUDIO` is missing, `VoiceTranslationService.promoteToForeground()` intentionally declines promotion and stops itself, but Android still treats the foreground-service start contract as unfulfilled and terminates the app process.

## Acceptance criteria

- [x] Neither mode calls `startForegroundService()` while its required runtime permissions are missing.
- [x] Entering either mode requests microphone permission before starting/binding the service.
- [x] Grant resumes connection once; denial is recoverable and clears the persisted crash-loop route.
- [x] API 36 denied-permission cold launch remains alive beyond the foreground-service deadline with no FATAL/ANR.
- [x] Granted-permission WalkieTalkie startup still produces a foreground service with the microphone type.
- [x] Focused tests and the full JVM/lint/instrumentation gates pass.
- [ ] The same two physical phones confirm Conversation and WalkieTalkie no longer terminate.

## Implementation evidence

Commit `a9d04d73621276f7d5390d25e9e2ec49f21e136e` performs a caller-side permission preflight before either foreground-service start and makes both mode fragments request microphone permission before connecting. A denial stores the safe Pairing route and exits the voice mode without touching a null communicator; a grant resumes the connection once. This also fixes the secondary denial-path `NullPointerException` found while exercising `ButtonMic.deactivate()` before a communicator existed.

On Pixel 7a API 36, a persisted Walkie cold launch with `RECORD_AUDIO` denied displayed the permission request and stayed alive beyond nine seconds with no service record or FATAL. Denial returned to Pairing and a later force-stop/relaunch remained stable. With the permission granted, Walkie started a foreground service with type `0x80` (microphone), remained alive beyond the deadline, and produced no FATAL. The clean repository gate passed 189 JVM tests, 24 instrumentation tests, lint with 0 errors/122 warnings, debug and unsigned release assembly, and R8 privacy verification.

## 2026-09-29 deep-audit residual

The permission request is still owned by the transient `VoiceTranslationFragment.waitingForServicePermission` boolean. It is neither saved nor restored, and the fragment uses the deprecated `requestPermissions()` callback. If the Activity/Fragment is recreated while the system permission UI is open, the result can arrive with `waitingForServicePermission == false`: a grant does not resume the service connection, while a denial does not clear the persisted voice-mode route and exit safely. Several input callbacks also dereference `voiceTranslationServiceCommunicator` without a lifecycle-safe boundary.

Android explicitly requires any state needed to interpret a result to be saved/restored because the process or Activity can be destroyed between launch and callback, even when using the Activity Result APIs.

### Additional acceptance criteria

- [ ] Permission-result ownership survives configuration change and process/Fragment recreation.
- [ ] Grant reconnects exactly once; denial/permanent denial clears the persisted voice mode and returns to Pairing exactly once.
- [ ] Voice controls cannot call a null or stale communicator during permission, bind, stop, or recreation transitions.
- [ ] Instrumentation forces Activity/Fragment recreation while the permission request is pending, followed by both grant and denial.
