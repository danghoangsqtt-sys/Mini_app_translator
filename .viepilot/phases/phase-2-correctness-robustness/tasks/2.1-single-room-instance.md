## Plan

Establish an application-context-backed singleton or injected `AppDatabase`, route both managers through it, and keep database calls off the main thread. Check that existing `consumption_credit_dp` data opens unchanged; no schema bump is needed unless the schema itself changes. Add an instrumentation regression showing both managers share the same database/DAO behavior and existing rows survive restart.

## File-Level Plan

|---|---|---|
| `database/AppDatabase.java` | Add a thread-safe, process-wide `getInstance(Context)` using the existing database file name and the application context. | There must be exactly one production `Room.databaseBuilder` path and no Activity-context retention. |

## Implementation Notes

- Use a `volatile` singleton with double-checked locking; build only from `context.getApplicationContext()`.
- Keep the database name `consumption_credit_dp`, Room schema version `1`, entities, DAO queries, and migration policy unchanged. This task changes ownership only, so existing on-device rows must open unchanged.
- Do not introduce new main-thread queries or expand the existing `AsyncTask` usage; manager behavior stays asynchronous where it already is.
- Keep constructor signatures accepting `Context` so current callers remain source-compatible. Centralize all `Room.databaseBuilder` use in `AppDatabase`.
- The instrumentation test must clean only its test rows in `@After`; it must not alter production schema or use destructive migration.
