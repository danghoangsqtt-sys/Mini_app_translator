Obtain microphone/Bluetooth runtime permissions first. Exercise background start restrictions, screen lock, stop/restart and process recreation on API 34/36; preserve older-API behavior.

## Done when

- No missing-type or permission exception during supported voice workflows.
- Services stop and restart cleanly under the device matrix.
- Merged manifest and integrated 3.1/3.2 build checks pass.

## Entry Contract Refinement

`ConversationService` and `WalkieTalkieService` are the two foreground-service candidates because each inherits `VoiceTranslationService`. `FirstLanguageRecognizerService` and `SecondLanguageRecognizerService` are currently bound-only: audit their lifecycle and export policy, but do not assign a foreground-service type by default. `GeneralService` is abstract and is not a foreground-service candidate.

Review every `startService`, `startForegroundService`, and existing `startForeground` call. In particular, determine whether promotion only from `VoiceTranslationService.onUnbind()` meets current timing rules, and order microphone and connected-device runtime permissions before promotion. Choose `microphone` and/or `connectedDevice` only when the actual work and all platform prerequisites justify each type.

The device evidence must cover permission ordering, screen lock, background start restrictions, stop/restart, and process recreation on API 34 and 36, while retaining the API 23/31 behavior in the phase matrix.
